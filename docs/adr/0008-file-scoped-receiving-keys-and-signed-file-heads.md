# File-scoped receiving keys and independently signed File heads

Status: accepted (approved protocol amendment; implementation pending)

The v1 Directory listing commits each complete encrypted child entry, including the parent-wrapped *current* File content key. Replacing that key on every save therefore requires the containing Directory capability and a new Directory listing signature. A direct File read/write Collaborator must instead save independently without receiving the parent capability, parent ID/path, siblings, or a Directory-wide correlation key. This decision amends [ADR-0003](0003-client-held-content-keys-and-capabilities.md); it does not describe code already implementing v2.

## Decision

- Each File has its **own** P-256 HPKE receiving key pair per File/capability epoch. A purpose-bound symmetric Key envelope under the containing Directory capability protects its private key; authorized File editors receive only its public write target, opaque File-scoped key identity, and epoch. Never share a receiving target across a Directory. The public target is authenticated against the committed File head and cannot be replaced by an unauthenticated service response.
- On **every successful File save**, the browser generates a fresh independent random File content key. Using the maintained `mdwn/enc-v1` RFC 9180 HPKE suite, it wraps that key to the File receiving public key in a dynamic parent-entry `file-content-key` envelope. It also envelopes the **same** current key separately to each currently eligible direct-Grant device, scoped to that File and device, with current Grant generations bound by the signed recipient-set commitment. A Directory reader opens the parent-wrapped receiving private key, verifies it matches the signed public target, then opens the dynamic File-key envelope; a direct File reader receives its own device envelope and File-scoped material only. HPKE base mode does not authenticate the sender. Neither direct File reads nor writes return a Directory capability, parent ID/path, siblings, or a Directory-wide correlation key.
- Directory listing **v2** has a signed, encrypted *structural* head, domain-separated from v1, that commits child membership, kind, complete encrypted names/order, and the stable parent-wrapped receiving-key material for v2 File entries. It does not commit the changing File-key envelope. A separately signed *current File head* commits File identity and revision; content-key identity/epoch; receiving-public-key identity/epoch and public-key digest; current private representation and dynamic parent/recipient-envelope digests (plus the paired Public representation digest when active); and recipient-set version/commitment. A File head exposes only File-scoped opaque metadata. The approved Device registry authenticates both signers; Directory readers verify both heads and exact returned bytes, while direct File readers verify only the File head and their permitted bytes. Structural Directory revision/digest checkpoints remain; File revision/digest checkpoints reject rollback and same-revision forks. At unchanged File revision, only a guarded, monotonic receiving-key epoch change (rotation) or recipient-set version change (including Grant-generation changes and device provisioning) may change the signed head; a different digest for the same revision, epochs and recipient-set version is a fork. The service verifies the signing device's effective authority **at commit** for the specific transition (write for a save), along with the current recipient set. Retain the approved registry's signing-key provenance for an already committed head: later device/Grant revocation does not retroactively invalidate an authentic historical head. Grant/device provisioning at unchanged File revision advances the signed recipient-set version under a current-head guard; pending recipients are explicitly unprovisioned, never represented as having an envelope. A fresh device without a trusted checkpoint remains subject to the existing service-registry/history-replay trust limit.
- Save commits are atomic: the short transaction rechecks effective write permission, current Device proof/registry epoch, expected File revision and current head, the exact authorized File recipient-descriptor set (including current device registries and Grant generations), and rotation state. It validates signed head, recipient-set commitment and envelope/representation byte digests; then either installs *all* new private (and active Public) representations, wrappers, head and current pointers/revisions or changes nothing. A stale or incomplete recipient set, revoked signer, changed target/epoch, or blocked rotation cannot partly save. The Worker cannot prove that opaque recipient envelopes all contain the same plaintext key; that is a browser-honesty assumption, **not** a service guarantee.
- Owned recovery reaches receiving private keys through the owned Directory hierarchy, or a strictly Account-owned auxiliary `vault-recovery` envelope if a key cannot be reached there. No Grant-derived material enters the recipient's Vault-root, recovery, or enrollment envelopes. When a party who may have learned a File receiving private key loses scope (notably loss of Directory access or a move out of a shared subtree), replace the **receiving key pair**, not just its wrapping envelope. First remove authorization, advance affected epochs and block writes; then use bounded resumable browser-driven rotation to issue new keys/wrappers/heads for remaining authorized readers. Device removal remains the narrower ticket-13 operation, without general File/Directory rekeying. Previously downloaded material cannot be recalled.

## Version boundary and migration

The original v1 listing and symmetric parent-entry File-key envelope remain explicitly versioned and readable until migration. A v1 listing still commits the **complete** encrypted entry bytes, including `keyEnvelope`; no decoder may silently omit that field, reinterpret the ciphertext, or fall back from failed v2 verification to v1. A v2 listing may carry explicitly tagged unmigrated legacy File entries, committing their complete v1 entry bytes until each is upgraded; only v2 File entries use independent File heads and stable receiving-key commitments.

SQL cannot decrypt or convert an old File. Before completing a **direct-write** File Share, a write-authorized browser holding the parent Directory capability atomically verifies the current v1 structural head and File revision, creates the File-specific receiving pair and parent wrapper, wraps the existing current File key for the new target and eligible direct devices, and signs/persists the v2 listing and File head under structural and File guards. The explicit one-time v1→v2 transition may preserve the existing representation/key and File revision; it binds the prior complete v1 commitment and current representation to the new signed head, advances the structural revision, and establishes the v2 File checkpoint. Thereafter every successful save advances File revision with a fresh File key; same-revision head changes require the guarded key-epoch or recipient-set-version transition above, never an arbitrary re-sign. A race, missing parent capability, or failed verification leaves v1 current and the direct-write Share uncompleted. New Files may begin in v2 once implemented. Migration requires no permanently online Owner: any authorized parent-capability browser can upgrade, and later authorized direct File editors save via the public target alone.

## Consequences

This deliberately rejects a symmetric Directory-wide wrapping target: distributing it to direct File editors would reveal sibling authority or correlation, while omitting the complete entry bytes from v1 commitments would silently weaken its integrity contract. v2 needs versioned signed-head storage, authenticated public write targets, File-level checkpoints, exact recipient-set/Grant-generation guards and rotations that replace exposed receiving pairs. The envelope framing and established purpose numbers in [`docs/enc-v1.md`](../enc-v1.md) remain unchanged; a new purpose is appended for the receiving private-key wrapper. See the amended [buildable specification](../buildable-spec.md#4-cryptographic-system) for the pending implementation contract.
