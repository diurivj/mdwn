# Owner-sealed copy of the Public link

ADR-0003 keeps a Publication's read capability in the Public link's fragment, "never sent in HTTP requests, logs, or referrers", and the Publish panel kept the complete link only in the memory of the page that created it. Owners lost their own link on every reload or other device: the panel could not show it, and making Comments public again asked them to paste it back. Ticket 68 changes that, and amends ADR-0003's wording to: the fragment never travels in a URL, header, log or referrer, and the service never holds it in readable form.

When the Owner's browser creates or rotates a link it also sends an **Owner link copy**: the link's 32-byte P-256 scalar sealed as an enc-v1 `vault-recovery` envelope under the Owner's Vault root key, with context `vaultId` = Owner, `objectId` = path ID, `keyId` = Publication ID, `keyEpoch` 1, `revision` 1. The Worker checks only its header binding and size (at most 1 KiB) and stores it beside the link's public key in `publication_links.owner_link_envelope`. Only the Owner's panel read returns it, and only the Owner's browser opens it, to show and copy the complete link and to seal a public Comment epoch. The copy follows its link row: rotation replaces it, Unpublishing and File hard deletion remove it, and a link row still never changes in place, so a link created without a copy never gains one; the Owner replaces such a link with a new one instead.

This is the same trust the Owner's recovery envelopes for Comment audience epoch capabilities already carry. Anyone with the Owner's Vault root key can read every active link, but that key already opens every File the link exposes. The service cannot read or forge a copy; like its control over which link is active, it could withhold a copy or serve a retired link's copy with that link's identity, which shows the Owner a link that does not work, never a reader a wrong document. Collaborators, editors and Public readers never receive it.

Rejected: keeping links in per-device browser storage, which fails on the Owner's other devices and breaks the rule that complete links are never persisted in the browser; and a new enc-v1 purpose, which would add a wire-format entry and cross-engine vectors without adding protection, since the Vault-recovery envelope already gives Owner-only authenticated encryption and path IDs (43 base64url characters) can never collide with the UUIDv7 epoch and capability identifiers of the other recovery envelopes.
