# Parent-free File capabilities

Direct File editors may edit Markdown but must receive neither the containing Directory capability nor its signed listing. The previous hierarchy wrapped each fresh representation key directly in that listing, making these requirements incompatible. We now place a random File capability between the Directory capability and fresh per-save File content keys. The File capability is stable only between access-driven rotations; direct Grants deliver it without disclosing parent or neighbouring content.

Ordinary converted-File saves atomically replace a signed File head, representation and File-capability-wrapped content-key envelope under live write authority, expected File identity/revision and capability epoch, without changing parent metadata. Existing encrypted Files require browser-driven, conditional conversion: rewrap the existing content key beneath a new File capability and update its parent edge/listing together, preserving content ciphertext. Interrupted conversion leaves wholly legacy or converted state. The service never generates or opens keys.

Per-generation device envelopes were rejected as the primary save mechanism: every save would need complete current recipient/device coverage and they do not by themselves repair the parent-listing dependency. Directory inheritance must continue without per-descendant device fanout. Revocation and scope exits still require replacement of affected capabilities before lifting write seals; stable does not mean permanently reusable after access loss.

Ticket 17 owns the authorization policy, current tree/sharing enforcement, parent-free saves and the basic current-device Grant-delivery prerequisite. Ticket 18 builds further provisioning and later capability kinds on that foundation; ticket 19 owns resumable rotation, and ticket 20 owns enrollment/replacement-device fulfillment. Comment, Publication, Import and Export tickets retain their own transactional enforcement and operational tests. This split avoids making ticket 17's completion depend on its own successors and does not waive the assembled MVP permission matrix.
