# Private sharing server (tickets 17, 18, 21)

All operations are resource **actions** under `/api/private/sharing/*`, never SSR loaders. They require a bound active Encryption device, same-origin request and a method/body-bound Device proof. Every mutation uses an invocation-specific, transaction-local `sharing_write_witnesses` row; a prior durable `device_proof_uses` row cannot authorize later statements. The witness is deleted inside the same atomic D1 batch. Replayed/colliding proofs cannot clean up a different invitation or advance a barrier. `X-Mdwn-Sharing-Budget` is a local-only diagnostic header, formatted `executedQueries;maxBoundParameters`; production and preview never emit it. The per-request DB proxy counts Session and device-auth queries, preflight reads, and *all* batch statements; it rejects >50 executed statements or >100 bindings per statement before execution. No query text or private data is logged.

## Browser wire contract (base64url byte strings)

`app/sharing/provisioning-wire.ts` exports the precise pure types. `POST /direct-files/:fileId/bootstrap` has an **empty body** and returns `{ ownerId, fileId, currentHead, recipients, retained }` for an authorized *current* physical direct-File Grant device with a retained **current** File key. A current Grant without eligible material returns ciphertext-free `202 {error:"provisioning_required"}`; unauthorized requests return `404`. `retained` includes only the caller's device-scoped ciphertext/digest, content-key coordinates, and `provenance:{grantId,offerBytes,offerDigest,offerSignature,signerDeviceId,signerPublicKey}`. The Worker joins the retained `grant_labels` Owner-signed offer to its historically Owner-bound signer (the signer need not still be active); it verifies the signature and the exact Grant, Owner, recipient Account, target File, original label ID, key ID/epoch/revision, caller's physical device public-key digest, and retained ciphertext digest. It also checks the actual HPKE grant context. An old offer registry epoch is permitted when the same physical key remains active at the current epoch; the old signed head may predate this device. Missing, corrupted, or substituted provenance yields ciphertext-free `202`, not a key. A legacy NULL physical-key digest remains ineligible. There is **no Shared-as label ciphertext, Owner-copy ciphertext, File representation ciphertext, parent ID, path, sibling, Directory capability or parent envelope** in this response. The signed offer necessarily contains *opaque label IDs and digest commitments*; these cannot be selectively removed without breaking its signature and are neither label plaintext nor label ciphertext. The signed `currentHead.bytes` similarly contains the *opaque representation ID and digest commitment* required to sign an integrity-preserving transition, but not the representation or File contents.

Before opening/redistributing a retained key, the browser must verify `offerBytes` with `offerSignature`/`offerDigest` and the historically Owner-bound `signerPublicKey` supplied by this authenticated route (compare any independently pinned Owner signer), then check the offer's `signerDeviceId`, `grantId`, `ownerId`, `recipientId`, `targetId`, `kind:file`, `targetKeyId`, `targetEpoch`, `contentRevision` against bootstrap and the caller's own Account/device identity. Require its unique signed device descriptor to match the local physical transport public-key SHA-256 and the SHA-256 of the *exact* retained ciphertext, and verify the retained digest and HPKE context. Neither a digest nor HPKE base-mode open alone proves sender identity. A holder separately verifies `currentHead` against approved historical signer provenance, opens the now-authenticated retained File key, checks the signed recipient descriptors, then submits `PATCH /direct-files/:fileId/complete` with `FileProvisioningCompletion`: `expectedHeadDigest`, `expectedRevision`, `expectedRecipientSetVersion`, `signedHead:{bytes,digest,signature}`, and complete `recipientEnvelopes:[{deviceId,ciphertext}]` for **all** currently eligible direct devices. The Worker validates a same-revision recipient-set-only signed transition. The content key, File revision, receiving-key ID/epoch/public target, representation ID/digest, parent-envelope digest and Public commitment cannot change. The holder needs File-read authority, **not Markdown-edit permission**; no Owner online or parent capability is required. A transaction rechecks the Session/proof, current Grant and generation, the **same checked offer bytes/digest/signature, signer identity/public key and label ID**, retained key/device public key, head/revision/target, all live recipients and Grant generations, and rotation barriers before replacing the *complete* direct-envelope set. Success is `{status:"ready"|"provisioning",headDigest}` (a valid current Shared-as label is also required for `ready`); stale commitments return `409`. A failed write cannot update any head/envelope/proof. A new File content key from a later save makes retained old material ineligible: ticket 20 must provision new material, never reinstall it as current.

`POST /roots` returns at most 100 `{roots,nextCursor}` sorted by opaque Grant ID; repeat with `{cursor:nextCursor}` while non-null. `POST /invitations` similarly accepts independently optional `{incomingCursor,outgoingCursor,grantsCursor}` and returns `next` with three cursors. Empty request bodies preserve the prior first-page contract. Do **not** treat the first page as the complete Vault. One unprovisioned root returns only opaque Grant/target IDs, kind/permission/status and empty label fields, never its ciphertext/name. A Directory scope is returned only for a current device with a valid label and current capability, and a Directory path is preferred over an overlapping narrower direct File Grant; direct File scope has no path/parent. The browser must revalidate ready roots and current permissions on every continuation and support cursor pagination.

`POST /resolve` expects `{kind:"share-id",value:exactOpaqueShareId}` or `{kind:"handle",value:exactStoredLookupToken}`. It compares `value` byte-for-byte against `accounts.share_id` or `accounts.share_handle_lookup_token`; **no** `@` removal, Unicode normalization, case-folding or token derivation is implemented on the server. The browser's `encodeRecipientAddress` (`app/sharing/client.ts`) removes exactly one leading `@` and derives that token with `deriveShareHandleLookupToken` (`app/sharing/share-handle.ts`: ASCII letters, digits, `_` and `-`, case-folded, `sh1:` + SHA-256), refusing any other spelling before a request; an opaque share ID is sent verbatim. No route assigns a handle yet (no ticket owns claiming one), so handle addressing works only for stored tokens. There is no fuzzy search/directory listing.

## Durable work, rotation and cleanup

Migration 0012 adds detached offer/Shared-as ciphertext and per-device retained-current-key rows; 0013 adds ephemeral sharing witnesses, 0014 adds nullable retained-device public-key digest (old NULL rows fail bootstrap closed), 0015 adds durable `sharing_rotation_jobs`, 0016 backfills the original Directory-key identity and fixes root creation (0011's `legacy` default would otherwise make root Grant envelopes impossible), 0017 adds Account/device-binding triggers. Migrations 0010/0011 are untouched. `provisioning_needs` is an opaque, current-Grant/device/generation/registry work item without capability or name; `sharing_rotation_jobs` is a pending, cursor-ready ticket-19 work item keyed to the rotation barrier. Revocation/leave/permission change cuts authority, removes affected Grant envelopes/retained material and old needs, advances the barrier and queues/updates the **pending** job atomically; it does not pretend a rewrap completed rekeying. Ticket 19's executor (below) rotates keys and receiving pairs, advances epochs and drains the job, then the barrier, only when its last step commits. Ticket 20 must reconcile current recipients/labels/Comment capabilities on enrollment or after content-key change; bootstrap/completion here is *only* narrow direct-File current-key recipient-set work. Private Comment capability fulfillment in ticket 18 waits for ticket 21; Public audience material belongs to ticket 22+ and is outside tickets 15–21. Neither is faked by a File envelope.

FK deletion order: pending Share → `share_offer_labels` → `share_device_material` → `share_offers` → `share_material` → `shares`; active Grant removal → `grant_device_envelopes`, `grant_retained_material`, `provisioning_needs`, `grant_label_deliveries`, `grant_labels`, then `grants` (and, for a direct File with no remaining same-recipient path, `file_device_envelopes`). `rotation_barriers` must outlive `sharing_rotation_jobs`; ticket 19 deletes the job first, then the barrier on verified rotation completion. Ticket 16 cannot delete a target/Owner/device before its dependent Grants, Share offers, label/capability/retained rows, provisioning needs and pending rotation jobs/barriers are explicitly drained. No sharing-audit tombstone exists. RESTRICT relations and insert triggers reject dangling or cross-Account material.

## Key rotation (ticket 19)

Migration 0020 adds `sharing_rotation_jobs.mode`: `rekey` for revoke or leave, `reprovision` for a permission change. An upsert never weakens a pending `rekey`, and any further change restarts the job at a new barrier epoch with its cursor reset. It also makes `directories.capability_epoch` forward-only by exactly one, and requires an active Owner signer for an in-place re-signed offer. Every Directory context (entry names and orders, listing heads, child wrappers) binds the Directory's real capability epoch. The hidden root is never shared, so rotation never rekeys the Vault-recovery-wrapped root.

The Owner's browser runs the jobs (`app/sharing/RotationStatus.tsx` on owned Files pages; `app/sharing/rotation-client.ts`) through the Owner-only resource route `/api/private/rotations/*` (`app/sharing/rotation.server.ts`): `POST` lists jobs, `POST :target/next` describes the next step, and each step is one `PATCH`, CAS'd on the job's barrier epoch and cursor. The job's barrier admits only these writes. The last step deletes the job, then the barrier.

- **File target** (`PATCH :target/file`): a same-revision `recipient-set-update` head for exactly the live direct recipients, with the current File key re-sealed to each. A `rekey` also moves the Private thread to a new epoch under the same receiving pair: a direct reader never held it.
- **Directory permission change** (`PATCH :target/grants`): the current capability re-sealed to every label-ready device of each Grant under a **re-signed offer** (same share, label and owner copy; `materialRevision + 1`; current epoch and permission; new content digests). Recipients' unchanged `roots` verification accepts it as it accepted the original offer. A device without a current label delivery stays a provisioning need (ticket 20).
- **Directory rekey**: the frozen subtree's Directories and receiving Files in `(depth, id)` order; the cursor is the last completed `depth:id`.
  - A Directory step (`PATCH :target/directory`) installs a fresh capability at epoch + 1 and wraps it in the parent's entry (parent listing re-signed). It re-seals every entry: names and orders at the new epoch; child, legacy-File and receiving wrappers opened under the old key and re-wrapped with their contexts unchanged. It re-signs the Directory's own listing at the new epoch and re-seals every Grant on it.
  - A receiving-File step (`PATCH :target/receiving`) rotates the File's receiving pair under the already-rotated parent, sharing `app/tree/receiving-rotation.server.ts` with moves, and moves its thread to a new epoch.
  - `PATCH :target/finish` ends the job once nothing remains after the cursor. A parent always precedes its children, so a new key is only ever wrapped under a rotated one.

Bounds: at most 32 Grants and 256 label-ready devices on one Directory per step. A step shares the 1.5 MiB authenticated-body ceiling, so a Directory whose listing nears its 512 KiB cap cannot rotate in one step. Rotation cannot recall content, ciphertext or keys already downloaded; the UI says so. Device removal (ticket 13) stays narrower and creates no job.

## Private Comment threads (ticket 21)

Resource actions under `/api/private/comments/*` (`app/routes/api/private-comments.ts`, `app/comments/comments.server.ts`), metered and witnessed like sharing: `POST files/:fileId` reads one page (optional `{cursor}`, 200 oldest-first), `PUT files/:fileId/thread` creates the one Private thread, `POST files/:fileId/thread` returns only its key state to a parent-capability reader, `PATCH files/:fileId/thread/devices` provisions direct devices, `PUT files/:fileId/comments` posts, `PATCH|DELETE comments/:commentId` edits or hard-deletes. Every ciphertext SELECT and CAS rechecks `fileAccessGuard`, so a device that loses its last File-read path gets `404` and no thread material on its next request. Another author's Comment is indistinguishable from a missing one for editing; the Owner may delete any Comment and edit none but its own.

Each thread epoch has a random 32-byte key. Its `comment_thread_epochs` row carries an HPKE wrapper to the File's receiving key, which the Owner and Directory readers open with the receiving private key they reach through the parent capability. From epoch 2 it also carries the previous epoch key sealed under the new one, so history stays readable after rotation. Direct File readers hold no receiving key, so each of their devices gets a current-epoch envelope in `comment_thread_device_envelopes`; an insert trigger requires a current direct File Grant, an active device and the current registry epoch. Any current reader may create the thread (sealing to the receiving public key and to every current direct device) and may provision waiting direct devices. Until then a direct reader sees "Secure access to these comments is being prepared". A registry change makes a device's envelope stale; provisioning replaces it and drops envelopes of devices outside the current recipient set. Revoking or leaving the last direct File Grant deletes that reader's envelopes. Bodies (`comment-content`, plaintext `["mdwn/private-comment/v1", authorId, text]`) and per-thread Public-pseudonym declarations (`attribution`) are sealed under the current epoch key; triggers admit new or edited rows only at the current epoch, edits only at revision + 1, and never a changed author.

A v2 File move rotates the receiving pair and, in the same batch, starts thread epoch n + 1: a new key sealed to the new receiving key, the old key chained under it, and fresh direct-device envelopes. The Worker refuses a move that ignores an existing thread. Ticket 19 should reuse `parseThreadRotation`/`threadRotationGuard`/`threadRotationStatements` for its rekeys, and ticket 20 should fulfil waiting direct thread devices from the Owner's browser. Hard deletion drains Comments, attributions, device envelopes, epochs and threads before the File rows. A legacy (v1) File has no receiving key and therefore no thread until its next save migrates it.
