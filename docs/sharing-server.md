# Private sharing server: implementation handoff (17/18, not ticket completion)

All operations are resource **actions** under `/api/private/sharing/*`, never SSR loaders. They require a bound active Encryption device, same-origin request and a method/body-bound Device proof. Every mutation uses an invocation-specific, transaction-local `sharing_write_witnesses` row; a prior durable `device_proof_uses` row cannot authorize later statements. The witness is deleted inside the same atomic D1 batch. Replayed/colliding proofs cannot clean up a different invitation or advance a barrier. `X-Mdwn-Sharing-Budget` is a local-only diagnostic header, formatted `executedQueries;maxBoundParameters`; production and preview never emit it. The per-request DB proxy counts Session and device-auth queries, preflight reads, and *all* batch statements; it rejects >50 executed statements or >100 bindings per statement before execution. No query text or private data is logged.

## Browser wire contract (base64url byte strings)

`app/sharing/provisioning-wire.ts` exports the precise pure types. `POST /direct-files/:fileId/bootstrap` has an **empty body** and returns `{ ownerId, fileId, currentHead, recipients, retained }` for an authorized *current* physical direct-File Grant device with a retained **current** File key. A current Grant without eligible material returns ciphertext-free `202 {error:"provisioning_required"}`; unauthorized requests return `404`. `retained` includes only the caller's device-scoped ciphertext/digest and content-key coordinates. There is **no Shared-as label, File representation ciphertext, parent ID, path, sibling, Directory capability or parent envelope** in this response. The signed `currentHead.bytes` necessarily contains the *opaque representation ID and digest commitment* required to sign an integrity-preserving transition, but not the representation or File contents.

A holder verifies `currentHead` against approved historical signer provenance and their retained Grant envelope, opens the retained current File key, checks the signed recipient descriptors, then submits `PATCH /direct-files/:fileId/complete` with `FileProvisioningCompletion`: `expectedHeadDigest`, `expectedRevision`, `expectedRecipientSetVersion`, `signedHead:{bytes,digest,signature}`, and complete `recipientEnvelopes:[{deviceId,ciphertext}]` for **all** currently eligible direct devices. The Worker validates a same-revision recipient-set-only signed transition. The content key, File revision, receiving-key ID/epoch/public target, representation ID/digest, parent-envelope digest and Public commitment cannot change. The holder needs File-read authority, **not Markdown-edit permission**; no Owner online or parent capability is required. A transaction rechecks the Session/proof, current Grant and generation, retained key/device public key, head/revision/target, all live recipients and Grant generations, and rotation barriers before replacing the *complete* direct-envelope set. Success is `{status:"ready"|"provisioning",headDigest}` (a valid current Shared-as label is also required for `ready`); stale commitments return `409`. A failed write cannot update any head/envelope/proof. A new File content key from a later save makes retained old material ineligible: ticket 20 must provision new material, never reinstall it as current.

`POST /roots` returns at most 100 `{roots,nextCursor}` sorted by opaque Grant ID; repeat with `{cursor:nextCursor}` while non-null. `POST /invitations` similarly accepts independently optional `{incomingCursor,outgoingCursor,grantsCursor}` and returns `next` with three cursors. Empty request bodies preserve the prior first-page contract. Do **not** treat the first page as the complete Vault. One unprovisioned root returns only opaque Grant/target IDs, kind/permission/status and empty label fields, never its ciphertext/name. A Directory scope is returned only for a current device with a valid label and current capability, and a Directory path is preferred over an overlapping narrower direct File Grant; direct File scope has no path/parent. The browser must revalidate ready roots and current permissions on every continuation and support cursor pagination.

`POST /resolve` expects `{kind:"share-id",value:exactOpaqueShareId}` or `{kind:"handle",value:exactStoredLookupToken}`. It compares `value` byte-for-byte against `accounts.share_id` or `accounts.share_handle_lookup_token`; **no** `@` removal, Unicode normalization, case-folding or token derivation is implemented on the server. Current browser `resolveRecipient` strips `@` and sends raw text; that is **not** a valid general encoding of the stored optional normalized lookup token. Before enabling handle UI, define/use the same normalized token derivation at handle assignment and browser lookup, or send a previously supplied exact token. Opaque share-ID addressing already works. There is no fuzzy search/directory listing.

## Durable work, rotation and cleanup

Migration 0012 adds detached offer/Shared-as ciphertext and per-device retained-current-key rows; 0013 adds ephemeral sharing witnesses, 0014 adds nullable retained-device public-key digest (old NULL rows fail bootstrap closed), 0015 adds durable `sharing_rotation_jobs`, 0016 backfills the original Directory-key identity and fixes root creation (0011's `legacy` default would otherwise make root Grant envelopes impossible), 0017 adds Account/device-binding triggers. Migrations 0010/0011 are untouched. `provisioning_needs` is an opaque, current-Grant/device/generation/registry work item without capability or name; `sharing_rotation_jobs` is a pending, cursor-ready ticket-19 work item keyed to the rotation barrier. Revocation/leave/permission change cuts authority, removes affected Grant envelopes/retained material and old needs, advances the barrier and queues/updates the **pending** job atomically; it does not pretend a rewrap completed rekeying. Ticket 19 must rotate keys/receiving pairs, advance affected epochs and drain the barrier/job only after verified completion. Ticket 20 must reconcile current recipients/labels/Comment capabilities on enrollment or after content-key change; bootstrap/completion here is *only* narrow direct-File current-key recipient-set work. Ticket 18 Comment and Public audience material waits for ticket 21, not faked by a File envelope.

FK deletion order: pending Share → `share_offer_labels` → `share_device_material` → `share_offers` → `share_material` → `shares`; active Grant removal → `grant_device_envelopes`, `grant_retained_material`, `provisioning_needs`, `grant_label_deliveries`, `grant_labels`, then `grants` (and, for a direct File with no remaining same-recipient path, `file_device_envelopes`). `rotation_barriers` must outlive `sharing_rotation_jobs`; ticket 19 deletes the job first, then the barrier on verified rotation completion. Ticket 16 cannot delete a target/Owner/device before its dependent Grants, Share offers, label/capability/retained rows, provisioning needs and pending rotation jobs/barriers are explicitly drained. No sharing-audit tombstone exists. RESTRICT relations and insert triggers reject dangling or cross-Account material.
