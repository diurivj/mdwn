# Research: privacy-preserving abuse controls on Cloudflare

**Scope and status.** Research only, prepared 2026-09-16 for the claimed Wayfinder ticket. This does not select an architecture or resolve the ticket. “Fact” describes documented behaviour; “recommendation” is a design option for a later decision. Prices and limits are current-documentation facts, not a commitment that they will remain so.

## Constraints used in this research

Wayfinder is an unmonetized React Router/Workers application with one D1 database. Private Markdown and Comment bodies are browser-only E2E ciphertext; the service has only opaque IDs, authorization, sizes, server times, and bounded security metadata. A publication's read capability is in a URL fragment. Therefore an abuse control must not inspect or log decrypted/private content, nor receive a fragment.

## 2. Privacy-preserving rate-limit shape

### Facts that bound the design

* A Worker receives the connecting client IP in `CF-Connecting-IP`; Cloudflare offers a managed transform to remove visitor-IP headers when they are not needed. `X-Forwarded-For` is not a safe simpler substitute because it can contain a chain. [Cloudflare HTTP headers](https://developers.cloudflare.com/fundamentals/reference/http-headers/)
* Rich WAF rate-limit characteristics can include IP, a header, cookie, path and other fields on plans that offer them. Its NAT-support characteristic uses `_cfuvid`, a cookie-based visitor ID; visitors without it share a bucket. [Rate-limit parameters](https://developers.cloudflare.com/waf/rate-limiting-rules/parameters/) Cloudflare documents `_cfuvid` as set only with that option to distinguish visitors sharing an IP. [Cloudflare Cookies](https://developers.cloudflare.com/fundamentals/reference/policies-compliances/cloudflare-cookies/)
* That cookie would be a nonessential Cloudflare cookie for the product's public-reader policy. It also cannot supply an account-level rule for app authorization.

### Recommendation: layered, bounded application counters

Use short fixed or sliding time buckets, scoped to an action and a minimal principal; store a counter, expiry, and only the data needed to decide the next request. Reject before persistence/expensive crypto. Exact thresholds are product decisions, not research facts; begin conservatively, publish `429`/retry guidance, observe aggregate false positives, and tune.

| Surface | Independent keys to check | Suggested response shape / privacy point |
| --- | --- | --- |
| Registration (including challenge issuance and completion) | (1) global endpoint bucket, (2) short-lived **network bucket**, (3) optional browser-issued challenge nonce; never a prospective account identity | Tight burst plus longer window; back off/escalate to local PoW after failures. The network key is only to slow mass creation, not to identify a person. |
| Recovery-code attempts | (1) account/recovery-credential record, (2) session/request transaction nonce, (3) short-lived network bucket, (4) global endpoint bucket | Strong per-account cap prevents an attacker distributing guesses over networks; network/global caps prevent spray. Consume a recovery code only after all checks succeed. Responses must not disclose whether an account/code exists. |
| Session create/refresh/revoke endpoints | (1) account where known, (2) opaque session ID for refresh/revoke, (3) short-lived network bucket for unauthenticated create, (4) global endpoint bucket | Limit login/passkey ceremony starts and refresh churn separately. Revocation should remain available under attack if possible, with a low-cost authenticated/session bucket rather than a broad network block. |
| Authenticated public Comment post | (1) account, (2) publication opaque server ID, (3) account+publication, (4) short-lived network bucket, (5) global comment-post bucket | Apply a publication cap to protect a single public thread and an account cap to control repeat spam. The browser submits ciphertext; controls use only account/publication opaque IDs, server time, size, and outcome—not text or link capability. Owner hard delete is an administrative action, not a text classifier. |

**Network-key treatment (recommendation).** Obtain the edge IP only at the point of decision, normalize address representation, calculate a keyed HMAC (with a rotatable secret) over `purpose || time-epoch || normalized-IP`, and persist only that opaque bucket key and expiry; delete the raw IP immediately and never put it in logs. Prefer a short epoch-specific key/secret or equivalent deliberate rotation so the same address is not linkable across long periods or unrelated actions. Maintain separate purpose namespaces (for example, registration versus recovery), prevent joining them, and retain only enough overlap to service an active window. This reduces exposure but does not turn IP-based rate limiting into anonymity.

**Important caveat (fact).** Hashing alone may not anonymize IP-derived values. The ICO says pseudonymised data remains personal data for a party holding additional information and that indirect identifiability is enough; pseudonymisation is a risk-reduction measure, not a status change. [ICO: Pseudonymisation](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-sharing/anonymisation/pseudonymisation/) A fast unsalted IP hash is especially vulnerable to enumeration/linkage. A keyed HMAC, secret rotation, purpose separation, retention limits, and access control are safeguards, not a claim of anonymisation. Obtain jurisdiction-specific privacy/legal review before assigning a legal basis or privacy notice wording.

## 3. Browser PoW combined with Cloudflare controls

**Fact.** In a URI, the fragment is not sent in HTTP requests; RFC 3986 defines it as a secondary resource reference resolved by the user agent after retrieval. [RFC 3986 §3.5](https://www.rfc-editor.org/rfc/rfc3986#section-3.5) This is a protocol property, not a reason to log full browser URLs: client telemetry, referrers, errors, or scripts can still expose it if designed carelessly.

**Recommendation: local, endpoint-bound PoW.** For a protected non-public mutation, the Worker issues a short-lived opaque challenge ID, an expiry, difficulty, and random challenge bytes. The browser hashes locally until it finds a nonce meeting the disclosed target, then submits only `{challenge-id, nonce, operation}` to the same mutation endpoint. The Worker verifies cheaply, atomically marks the challenge spent, and applies the scoped counters. Bind the challenge server-side to the operation category and (where applicable) opaque account/session or publication **server ID**, not to plaintext, ciphertext, browser fingerprint, referrer, or public URL.

* Never construct a challenge `action`, `cData`, log field, query string, request header, or analytics event from `location.href`; the fragment must stay browser-local.
* On public publication pages, the fragment is only for the browser's decrypt/read capability. A Comment-post request should use the non-secret publication routing ID already required by the API plus signed-in authorization; it should never echo the read capability. Do not put an opaque fragment-derived value into a WAF URL/header/cookie characteristic.
* Keep challenge records bounded (one-use, short expiry, fixed-size), reject stale/replayed solutions, and cap challenge issuance/verification before D1 writes. Increase difficulty only for a locally measured abuse state; always offer an accessible, privacy-reviewed fallback rather than imposing a permanent computational barrier.
* A browser PoW deters cheap parallel automation but is not identity, bot detection, or DDoS protection. Cloudflare edge/WAF coarse limiting protects capacity first; application counters and PoW govern expensive/abuse-sensitive mutations.

**Turnstile combination (optional recommendation).** If selected later, render it only on the protected form/action, submit its token with the request, call Siteverify server-side, check expected action and hostname, and omit optional `remoteip` to minimize IP disclosure to Siteverify. Siteverify tokens expire in five minutes and are single use. [Siteverify](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/) Do not mix a secret fragment into Turnstile `action`/`cData`, and do not retain the response's optional metadata. This still delegates the security challenge to Cloudflare, so it requires an explicit product/privacy decision.

## 4. Minimal operational/abuse logging and privacy treatment

### Recommendation: an allowlist, not request logging

Store a bounded security event only for an outcome needing review, deletion, account enforcement, or aggregate tuning. Suggested fields: server timestamp; event type/version; allow/deny/reason code; coarse endpoint/action class; opaque account ID when signed in; opaque publication server ID only for comment controls; fixed size class (not body); PoW challenge state/difficulty; counter window/remaining or retry-after; and a short-lived purpose-scoped network HMAC only when necessary. Retain a small, predeclared duration matching the longest enforcement/appeal window, then delete/aggregate. Restrict staff access, document purpose/retention, and test the purge path.

Do **not** store or log: Markdown/comment plaintext or ciphertext, decryption material, recovery code plaintext or hash outside the credential's necessary verifier, passkey assertion payloads, raw IPs, full `CF-Connecting-IP`, `X-Forwarded-For`, raw User-Agent, fingerprint/JA3/JA4, full URLs, `Referer`, query strings, cookies, authorization/session tokens, Turnstile token, public-link fragment, or an event stream that becomes behavioural analytics. A `CF-Ray`/request correlation ID can itself be linkable; keep it only for a narrowly time-bounded incident workflow if its benefit is established.

**Fact.** Workers Logs can collect invocation logs and all logs in the request context; free retention is three days and logs are sampled by configurable head sampling. [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) **Recommendation:** configure minimal observability and audit framework/error defaults so they do not serialize URLs, headers, bodies, or environment values. Security records should be intentionally shaped rather than emitted through `console.log`.

## 5. Non-content moderation and anti-spam for public comments

Because the service cannot decrypt content, controls must be metadata/authority-based. The following are recommendations, not claims that they identify “bad” content:

1. **Admission friction:** require a valid signed-in, passkey-backed account; apply registration PoW/counters; delay or cap early account activity; rate-limit comment mutations as above. Never require reader tracking/cookies for read access.
2. **Posting limits:** cap comment byte size/count, attachment-free scope, per-account and per-publication burst/long windows, duplicate mutation IDs, and number of active publications an account can touch in a window. These operate on server-known opaque IDs, sizes, and times.
3. **Authority controls:** preserve Owner ability to hard-delete any comment; add bounded account-level disable/suspension and revoke all sessions for repeated policy/abuse events. Record only the enforcement reason category, actor/subject opaque IDs, timestamp, expiry/review state, and appeal/reversal outcome—not comment text.
4. **Abuse reporting without server-readable text:** a report can name only an opaque comment ID and category. Rate-limit reports and prevent self-report floods. A report is a signal for Owner/account controls, not evidence that lets the service inspect ciphertext.
5. **Resilience:** make delete/suspend/idempotency operations available even under comment-post limits; use generic errors to reduce account/recovery enumeration; validate authorization on every mutation; make application checks atomic to prevent concurrent bypass.
6. **No tracking substitutes:** do not adopt behavioural fingerprinting, ad/analytics SDKs, IP-with-NAT-support `_cfuvid`, or a third-party CAPTCHA merely to gain granularity without a separate product/privacy decision. Cloudflare documents that `_cfuvid` is a visitor-distinguishing rate-limit cookie. [Cloudflare Cookies](https://developers.cloudflare.com/fundamentals/reference/policies-compliances/cloudflare-cookies/)

## Later-decision checklist

- [ ] Choose free-only versus Workers Paid ($5/month minimum) and an explicit maximum spend/alert policy; re-check current pricing immediately before deployment.
- [ ] Decide whether one Free WAF path-only rule is worth consuming; do not treat it as account/network rate limiting.
- [ ] Set action-specific counter windows/thresholds, explicit false-positive handling, and a quota-exhaustion response; estimate resulting D1 reads/writes under abuse.
- [ ] Decide D1-only counters versus a narrowly scoped hibernatable SQLite DO only after concurrency/load testing.
- [ ] Specify browser PoW algorithm, maximum difficulty/device-cost/accessibility fallback, one-use expiry, and no-fragment data-flow test.
- [ ] Decide whether Turnstile is acceptable as a disclosed fallback despite the no-third-party-CAPTCHA preference; if yes, document Siteverify, optional-IP omission, and token/log redaction.
- [ ] Approve the exact security-event schema, retention, key rotation, staff access, deletion/purge test, and privacy notice/legal review. State explicitly that IP HMACs are pseudonymous and hashing alone may not anonymize.
- [ ] Define Owner delete, report, account-suspension, session-revocation, appeal, and repeat-abuse rules without attempting server-side content moderation.
