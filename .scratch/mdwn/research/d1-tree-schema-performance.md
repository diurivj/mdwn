# D1 adjacency-list tree: performance findings

## Verdict

**Yes—for a personal-first, low-concurrency vault, a typed `vault_nodes` table with `parent_node_id` and bounded recursive CTEs is a sound D1 design.** SQLite explicitly supports recursive CTEs for tree traversal, and D1 uses SQLite semantics/query engine. The ordinary paths—list a directory's direct children, walk one ancestor chain, or enumerate a modest shared subtree—should be fast when the recursive join is indexed. This conclusion is conditional on bounding traversals, validating actual plans, and treating bulk subtree mutations as maintenance work rather than a normal request-path operation. [SQLite WITH](https://www.sqlite.org/lang_with.html), [D1 query SQL](https://developers.cloudflare.com/d1/best-practices/query-d1/)

## Evidence and design implications

- **Recursive traversal is a supported SQLite primitive.** SQLite documents recursive CTEs as the facility for hierarchical/tree and graph queries; a `WITH RECURSIVE` CTE may prefix `SELECT`, `INSERT`, `DELETE`, or `UPDATE`. D1 says it is compatible with SQLite SQL conventions because it uses SQLite's query engine. Therefore recursive CTEs are an appropriate mechanism for descendant enumeration and ancestor-based authorization, subject to an integration test against the deployed D1 version. [SQLite WITH](https://www.sqlite.org/lang_with.html), [D1 query SQL](https://developers.cloudflare.com/d1/best-practices/query-d1/)

- **Index the recursive edge.** Create an index whose leftmost column is `parent_node_id` (normally `CREATE INDEX ... ON vault_nodes(parent_node_id)`). Every recursive descendant step is effectively a lookup for children by parent. Cloudflare says indexes reduce scanned rows for predicates and joins and recommends confirming use with `EXPLAIN QUERY PLAN`; SQLite's foreign-key documentation likewise says unindexed child-key checks force linear scans and recommends indexes on child-key columns in real systems. If direct-child listing has a stable presentation order, use a composite index beginning with `parent_node_id` followed by that order key only after verifying the query plan. [D1 indexes](https://developers.cloudflare.com/d1/best-practices/use-indexes/), [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html)

- **Use integrity constraints, but do not confuse them with cycle prevention.** D1 enforces foreign keys by default, equivalent to `PRAGMA foreign_keys = on`; a self-reference can ensure a non-root parent exists. It cannot ensure that a move does not make a node a descendant of itself. The move operation must first reject that condition (for example, with a bounded recursive ancestor/descendant check) and then update the one `parent_node_id`. Prefer `ON DELETE RESTRICT` unless recursive deletion is an explicit product operation; `CASCADE` propagates deletes to dependent child rows. [D1 foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/), [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html)

- **Bound recursive work.** SQLite explains that `UNION ALL` retains duplicate generated rows whereas `UNION` deduplicates; for a guaranteed tree with enforced cycle prevention, `UNION ALL` avoids unnecessary duplicate tracking. Carry a depth if needed, impose a maximum traversal size with `LIMIT`, and do not rely on the current undocumented FIFO behavior when no recursive `ORDER BY` is supplied. SQLite specifically recommends `LIMIT` as a safety where an upper bound is known. These protections matter for corrupted/cyclic data and unexpectedly broad directory shares. [SQLite WITH](https://www.sqlite.org/lang_with.html)

- **Recursive shares are read-cost proportional to the traversed subtree.** A direct share lookup is constant-ish with an index on its grant key (for example `(principal_id, node_id)` as dictated by authorization query shape); a recursive share check adds ancestor traversal. This is acceptable at the stated scale, but avoid running a separate recursive query per displayed node. Resolve the shared root(s) once, fetch the subtree with one bounded CTE, and inspect `meta.rows_read` plus `EXPLAIN QUERY PLAN` on representative large trees. D1 bills/counts scanned rows, not only returned rows. [D1 indexes](https://developers.cloudflare.com/d1/best-practices/use-indexes/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)

## D1 operational limits and caveats

- **Per-database serialization is the main scaling constraint.** Each D1 database is single-threaded and processes one query at a time; excess concurrency queues and can become an `overloaded` error. This is compatible with personal/low-concurrency use, but concurrent editors, automatic rekey jobs, or bulk deletes can delay all other requests to that database. Keep request-path transactions short and retry documented transient write failures with exponential backoff and jitter. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 retry queries](https://developers.cloudflare.com/d1/best-practices/retry-queries/)

- **Keep mutations small and atomic.** D1 `batch()` executes prepared statements sequentially as one SQL transaction and rolls the sequence back on failure, so it suits a single move plus related audit/share updates. D1's 30-second SQL duration also applies to the *entire* batch. It has a 100-parameter limit, 100-KB SQL-statement limit, and Free allows 50 D1 queries per Worker invocation (1,000 Paid). [D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)

- **Do not perform large recursive delete/rekey in one statement or one request.** Cloudflare expressly says large `UPDATE`/`DELETE` operations affecting hundreds of thousands of rows or hundreds of MB exceed execution limits and must be batched (example: 1,000 rows at a time). A subtree delete can additionally cascade into files, shares, comments, and indexes; an access-control rekey that touches every descendant has the same risk. Make such jobs resumable/idempotent, chunk by stable node IDs, and expect temporary contention; first mark/lock the subtree or otherwise prevent new descendants while the job runs. The last two points are operational design recommendations inferred from D1's stated serialization and batch guidance. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)

- **Indexes are a read/write trade-off.** D1 says an indexed-column write also writes the index row, and indexes consume storage, while indexed predicates sharply reduce reads and latency. For this vault, the `parent_node_id` index is essential; add share and sibling-name/order indexes only to serve measured queries. On Free, limits are 5 million rows read/day and 100,000 rows written/day, and hitting either prevents further queries until the daily reset. [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)

## Decision boundary

Choose adjacency list + recursive CTEs now if most operations are direct-child browsing, occasional ancestry checks, and modest recursive shares. Revisit materialized paths, closure tables, or precomputed authorization only if metrics show large/deep recursive traversals or high concurrent mutation volume. Those alternatives trade the simple O(1)-row move of an adjacency list for more write amplification and their own expensive subtree maintenance; they are not justified by the stated workload.
