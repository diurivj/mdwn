# 17: Shares and Grants: invite, accept or decline, effective access, permission matrix

**What to build:** An Owner invites an existing Account to read or read/write one Directory subtree or one File by exact handle or opaque identifier, the recipient accepts or declines, and server-side authorization then enforces the full permission matrix — including content a Collaborator creates, which belongs to the Owner.

**Blocked by:** 09 (Device proofs and registry epochs), 14 (Private tree).

**Status:** needs-info

- [x] A Share targets either one Directory or one File and proposes `read_only` or `read_write`; it addresses an existing Account by its unique exact-match handle or opaque share identifier, with no Account directory or fuzzy discovery.
- [x] A pending Share is unique per Owner, recipient, and target; the Owner may cancel it, the recipient may accept or decline it, and acceptance creates one active Grant per Owner, recipient, and target.
- [x] A Directory Grant covers the current subtree and future descendants; a direct File Grant follows File identity through Owner-controlled rename and move and exposes no path, parent, siblings, or neighbouring tree content.
- [ ] Direct File read/write permits Markdown edits only — never rename, move, delete, import targeting, or structural access.
- [ ] Every row of the permission matrix is enforced server-side: read private File/metadata in scope, edit Markdown, create a child File/Directory, rename/reorder/delete/move, use a Directory as an Import target, read/create Private Comments, edit/delete one's own Private Comment, hard-delete another author's Comment, manage Shares, manage a Publication, request a Publication, read Collaborators-only Public Comments, read and post public-audience Public Comments, and export (owned Files only).
- [x] Effective File access is the union of active direct and inherited Grants, derived by a bounded indexed recursive CTE over ancestor Directories plus exact direct File Grants; the strongest permission controls Markdown and structural authority, while `can_read_private_comments` and `can_read_collaborators_public_comments` are independent Booleans.
- [x] Overlapping Grants remain independent and are deduplicated when deriving effective authority, so revoking one Grant cannot remove access supplied by another; the Owner may change permission or revoke and a Collaborator may leave.
- [ ] Content a Directory read/write Collaborator creates manually or through Import belongs immediately to the target Directory's Owner, with no approval workflow, no new Share or Grant, and no ownership transfer; the initiator keeps access through the existing Directory Grant.
- [x] Cancelled or declined Shares and revoked Grants are hard-deleted after any bounded security retention, and the MVP keeps no historical sharing-audit log.
- [ ] Tests cover the full matrix including read-only Private Comment participation and direct-File structural denial, overlapping-Grant union and independent revocation, and reviewed `EXPLAIN QUERY PLAN` output for the effective-access query.

## Comments

- 2026-10-01: Server-authority implementation adds exact-address invitation/accept/decline/cancel, independent active Grants, permission changes/revoke/leave, the complete permission-policy interface, bounded indexed effective access, and transactional tree enforcement. Directory read/write Collaborators create and save Owner-owned content and can rename/reorder/move/delete within a common covering scope. Direct File reads and ancestry never expose a parent or neighbouring content. Hard deletion explicitly removes dependent sharing records. See `docs/sharing.md` for the protocol, reviewed query plan, and inter-ticket safety seals.
- 2026-10-01: **Remaining dependency/design gap:** the existing fresh-key File save requires a parent-wrapped key and an encrypted signed Directory listing. A direct File editor must receive neither. Its server write permission is derived, but the route currently fails closed with `409 shared_content_provisioning_required`; no save is falsely reported as successful. Ticket 18 must supply a coordinated parent-free fresh-key persistence/read contract for every Owner/inherited/direct access path. Choosing a stable per-File capability would change the ADR-0003 hierarchy; per-generation recipient envelopes need complete recipient/epoch coverage. The direct-edit and full-enforcement checkboxes remain open rather than claiming the ticket complete. Future Comment/Publication/Import/Export endpoints also need to apply the policy interface in their own stored-author/current-epoch transactions; those features remain in their existing tickets. Manual creation already preserves Owner identity; Import ownership and endpoint-level full-matrix tests remain open.
- 2026-10-01: Revocation/leave/permission changes atomically seal future writes, and moves that would remove inherited readers are explicitly refused. Ticket 19 must complete browser-driven rotation before unsealing; reads and privacy-preserving hard deletion remain available. The seals are current target state, never retained recipient/Grant history.
