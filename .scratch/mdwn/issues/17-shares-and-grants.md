# 17: Shares and Grants: invite, accept or decline, effective access, permission matrix

**What to build:** An Owner invites an existing Account to read or read/write one Directory subtree or one File by exact handle or opaque identifier. Acceptance atomically provisions current-device root capabilities and creates a Grant. Define the full server permission policy and enforce it in existing sharing/tree endpoints, including parent-free direct File edits and Owner ownership of manual Collaborator creation. Later feature tickets own their corresponding operational enforcement, ownership and endpoint tests; this split is recorded in ADR-0008 and does not waive the assembled MVP matrix.

**Blocked by:** 09 (Device proofs and registry epochs), 14 (Private tree).

**Status:** done

- [x] A Share targets either one Directory or one File and proposes `read_only` or `read_write`; it addresses an existing Account by its unique exact-match handle or opaque share identifier, with no Account directory or fuzzy discovery.
- [x] A pending Share is unique per Owner, recipient, and target; the Owner may cancel it, the recipient may accept or decline it, and acceptance creates one active Grant per Owner, recipient, and target.
- [x] A Directory Grant covers the current subtree and future descendants; a direct File Grant follows File identity through Owner-controlled rename and move and exposes no path, parent, siblings, or neighbouring tree content.
- [x] Direct File read/write permits Markdown edits through a stable-between-rotations File capability, never parent access, rename, move, delete, import targeting, or structural access. Fresh representation keys, signed File heads and live transactional authorization are independent requirements.
- [x] Every permission-matrix row has a server policy contract. Existing sharing/tree endpoints enforce read, edit, create, rename/reorder/delete/move and Owner-only Share management inside their transaction. Tickets 21–23 enforce Comment/Publication operations, 28 enforces owned-only Export, and 29–30 enforce Import targeting/ownership, with their stored-author/current-epoch conditions and operational tests.
- [x] Effective File access is the union of active direct and inherited Grants, derived by a bounded indexed recursive CTE over ancestor Directories plus exact direct File Grants; the strongest permission controls Markdown and structural authority, while `can_read_private_comments` and `can_read_collaborators_public_comments` are independent Booleans.
- [x] Overlapping Grants remain independent and are deduplicated when deriving effective authority, so revoking one Grant cannot remove access supplied by another; the Owner may change permission or revoke and a Collaborator may leave.
- [x] Manual content creation immediately preserves the Directory Owner, including converted-File creation signed by the Collaborator's device; no approval, new Grant or ownership transfer. The same ownership invariant is a required dependency for final Import commit in ticket 30.
- [x] Cancelled or declined Shares and revoked Grants are hard-deleted after any bounded security retention, and the MVP keeps no historical sharing-audit log.
- [x] Tests cover the full policy matrix and current endpoint enforcement, direct-File structural denial and real parent-free saves, overlapping authority, independent revocation, Owner identity, acceptance key delivery and reviewed real-D1 `EXPLAIN QUERY PLAN`. Future feature tickets own their operational matrix tests, including read-only Private Comment participation.

## Approved integration split

- Ticket 17 includes stable File capabilities, signed parent-free saves, atomic legacy conversion, current-device root Grant delivery/acceptance and browser shared-root navigation. New browser-created Files use the new hierarchy; ciphertext and keys never enter SSR.
- Ticket 18 extends provisioning to Comment/Public-history material and opaque provisioning-needs orchestration. Ticket 20 handles automated new/replacement-device fulfillment. Grant capabilities remain excluded from owned-root recovery/enrollment.
- Ticket 19 retains resumable capability rotation. Current authority deletion and write seals are not completed rotation; no seal may be cleared without replacing affected capabilities and current envelopes.
- The approved server/key-delivery slice is implemented, verified and reviewed. The sharing-management panel is not included. PR #21 remains draft until merge readiness is agreed; fresh green CI is required before merge.

## Comments

- 2026-10-01: Server-authority implementation adds exact-address invitation/accept/decline/cancel, independent active Grants, permission changes/revoke/leave, the complete permission-policy interface, bounded indexed effective access, and transactional tree enforcement. Directory read/write Collaborators create and save Owner-owned content and can rename/reorder/move/delete within a common covering scope. Direct File reads and ancestry never expose a parent or neighbouring content. Hard deletion explicitly removes dependent sharing records. - 2026-10-01: **Remaining dependency/design gap:** the existing fresh-key File save requires a parent-wrapped key and an encrypted signed Directory listing. A direct File editor must receive neither. Ticket 18 must supply a coordinated parent-free fresh-key persistence/read contract for every Owner/inherited/direct access path. Choosing a stable per-File capability would change the ADR-0003 hierarchy; per-generation recipient envelopes need complete recipient/epoch coverage. The direct-edit and full-enforcement checkboxes remain open rather than claiming the ticket complete. Future Comment/Publication/Import/Export endpoints also need to apply the policy interface in their own stored-author/current-epoch transactions; those features remain in their existing tickets. Manual creation already preserves Owner identity; Import ownership and endpoint-level full-matrix tests remain open.
