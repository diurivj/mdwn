# 19: Key rotation on revoke, leave, permission change, and move out of a shared subtree

**What to build:** Revoking access, leaving a Share, changing a Grant's permission, or moving content out of a shared subtree immediately removes server authorization and makes the new state cryptographically true for future writes, through a resumable browser-driven rotation that never overpromises recall.

**Blocked by:** 16 (Move, reorder, delete, and bounded Directory hard deletion), 18 (Grant capability envelopes and shared-content provisioning).

**Status:** ready-for-agent

- [x] Revocation of a Grant, a leave, a permission change, or a shared-subtree revocation first removes server authorization in a short transaction, advances the affected capability/key epoch, and blocks new writes beneath the affected root.
- [x] It then creates a browser-driven, resumable, bounded Key-rotation job that rewraps current capabilities only for the remaining authorized devices.
- [x] The `crypto_jobs` record holds only opaque job identity, bounded cursor/progress, initiating/authorized Account, target/epoch, and lifecycle state — no plaintext key or content.
- [x] Rotation cannot recall previously downloaded plaintext, ciphertext, or keys, and the UI communicates that limit rather than implying deletion.
- [x] Routine Encryption-device removal (ticket 13) is deliberately narrower and does not rotate Vault, Directory/File, Grant, or representation keys.
- [x] A move out of a shared subtree completes its required rekeying within the bounded operation or is rejected/deferred; it may never leave future writes under an old capability.
- [x] The job is idempotent and resumable from an enrolled device after interruption, with observable progress and no duplicate rewrapping.
- [x] Tests prove server access is denied before rotation finishes, new writes under the affected root are blocked until it is safe, remaining authorized devices keep or regain current access after a proof refresh, no old-epoch envelope remains current, and an interrupted job resumes.

## Comments

- 2026-09-21: Dependency note from ticket 03: rewrapping uses `app/crypto/enc-v1` (`docs/enc-v1.md`). An envelope under a superseded epoch fails `stale-epoch`; a future epoch fails `unexpected-epoch` and must fail closed rather than start a rotation. The symmetric writer keeps nonce state in memory only: an interrupted or resumed job must re-seal with a fresh writer (new key namespace) or reuse stored bytes verbatim, and must never persist or restore nonce state.
- Approved, **not yet implemented**, amendment [ADR-0008](../../../docs/adr/0008-file-scoped-receiving-keys-and-signed-file-heads.md): when a removed party may have learned a File receiving private key (especially Directory-scope loss or moving out), replacing only its parent wrapper is insufficient—rotate the **receiving key pair** and update stable wrapper, File public target, dynamic content-key envelope and signed structural/File heads for remaining readers. Remove authorization, advance epochs/block writes first, then use bounded resumable browser-driven rotation; no old target can accept later writes. Ticket 13 device removal stays narrower; Grant-derived keys never enter recipient recovery/enrollment material.

  6. Ticket 16: a Directory move leaving shared scope is refused; a File move rotates the receiving pair and thread epoch within the move batch (`comments.test.ts`, `tree-structure.test.ts`).

When re-signing, the browser copies the stored offer's unchanged fields as served, and the Worker checks they equal the stored offer; verifying that stored offer's original signature in the browser too is a hardening follow-up. Devices without a current label are ticket 20's provisioning needs.
