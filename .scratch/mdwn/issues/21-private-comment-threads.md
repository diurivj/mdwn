# 21: Private Comment threads

**What to build:** Anyone with current File-read access reads and writes plain-text Private Comments on a File, under the author/Owner rules, with bodies and displayed pseudonyms decrypted only in the browser.

**Blocked by:** 04 (Vault key hierarchy, recovery secret, and capsule), 17 (Shares and Grants).

**Status:** ready-for-agent

- [x] Exactly one Private Comment thread exists per File; schema and migrations cover `comment_threads`, `comment_thread_epochs` (with the Private thread's current key epoch in a constrained representation), `comments`, and `thread_attributions`.
- [x] Every Private Comment thread has a capability enveloped to the Owner and to every currently authorized device with effective File-read access; participation depends only on current File-read access, not on read/write strength.
- [x] Comments attach to stable File identity only and form one flat ordered list: no replies, resolution/archive, reactions, attachments, mentions, embeds, or rich Markdown.
- [x] A Comment is plain text with line breaks, at most 2,000 characters; HTML and Markdown are never interpreted.
- [x] Every Comment displays the author's Public pseudonym; bodies and pseudonyms are ciphertext at the service boundary, and no Comment table stores plaintext or moderation-searchable text.
- [x] Authors may edit or hard-delete their own Comments only while they retain current thread access; the Owner may hard-delete any Comment but may never edit another author's body; there is no edit history or restore.
- [x] A read-only Collaborator sees **Read-only — you can comment** and keeps the normal Private composer.
- [x] UI: wide layouts switch the right preview pane to the Comment inspector; narrow layouts use the Comments content view; the authenticated composer sits at the bottom of the selected thread; **Private** is the default authenticated thread; the Private and Public threads load through separate endpoints and are never combined.
- [x] A device that loses its last File-read path immediately loses thread authorization, and no thread ciphertext is served to it afterwards.
- [x] Tests enforce the mutation rules server-side (author identity, Owner hard-delete exception, epoch and access checks), prove read-only participation, and prove a revoked device receives no thread material.

Triggers admit bodies and declarations only at the current epoch, edits only at revision + 1, never a changed author, and device envelopes only for an active device of a current direct Grant at the current registry epoch.
- Keys: the Owner and Directory readers open the thread through the File receiving private key; direct readers through their own device envelope. Any current reader creates the thread (sealed to the receiving public key and every current direct device) and provisions waiting direct devices; until then a direct reader sees "Secure access to these comments is being prepared" (ticket 20 will fulfil these from the Owner's browser). A v2 File move starts a new epoch sealed to the new receiving key in the move batch; hard deletion drains the thread; revoking/leaving the last direct Grant deletes that reader's envelopes; registry-stale envelopes are replaced on provisioning.
- Text and display: `app/comments/crypto.ts` normalizes CRLF to LF, refuses other controls and unpaired surrogates, and caps 2,000 code points; the author Account ID is inside the body plaintext. `app/comments/CommentsPanel.tsx` renders bodies with `whitespace-pre-wrap` as plain text and shows each author's decrypted Public pseudonym. Wide layouts switch the right pane between Preview and Comments (`Side pane` group); narrow layouts add a third `Comments` view; the thread label is a single pressed **Private** control (the Public thread, ticket 23, gets its own endpoint); the composer with an `x / 2000` counter sits at the bottom. Edit is offered only on one's own Comments, Delete on one's own or (Owner) any, with an inline permanent-deletion confirmation.
- Evidence: `tests/worker/comments.test.ts` (10 tests, real SELF.fetch + migrated D1 + WebCrypto, every route within the 50-query/100-binding budget): create race commits exactly one thread and the schema refuses a second; read-only direct Collaborator participates through a provisioned envelope and the service stores only ciphertext; any reader provisions, replays and foreign devices are refused, registry-stale envelopes are replaced; author-only edit (Owner edit of another body is a 404), stale revision 409, wrong-context 400, Owner delete-any, author delete-own, no reattribution or revision skip in storage; epoch/attribution/plain-text rules (2,000 emoji accepted, 2,001 characters and control characters refused, markup kept literal, oversize ciphertext refused, epoch jumps and non-current inserts refused); revoked device gets `404 {"error":"not_found"}` with no ciphertext on read, key read, post, edit and delete, and its envelopes are gone; pagination 200 + 1; legacy File has no thread; v2 move rotates to epoch 2 with history readable and the direct reader re-enveloped; Directory deletion drains every Comment table. `e2e/private-comments.spec.ts` (2 tests) passed on Chromium, Firefox and WebKit: a read-only Directory Collaborator sees "Read-only — you can comment", posts through the normal composer, edits their own Comment, has no controls on the Owner's, the Owner sees the pseudonym and hard-deletes it, D1 holds no body or pseudonym plaintext, and the narrow Comments view works; a direct File reader waits for its envelope, the Owner opening the thread provisions it, then the reader reads history and posts.
