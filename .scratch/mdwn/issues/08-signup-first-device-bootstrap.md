# 08: Signup: first-Encryption-device bootstrap, phrase gate, recovery codes

**What to build:** A new person creates an mdwn Account in one ceremony — proof of work, then a passkey — and lands signed in on a browser that is already a private-capable, device-bound Encryption device, with the Vault recovery phrase recorded and ten authentication recovery codes shown exactly once.

**Blocked by:** 03 (`mdwn/enc-v1` envelope library), 04 (Vault key hierarchy, recovery secret, and capsule), 06 (Accounts, passkeys, sessions), 07 (Abuse-control primitives).

**Status:** ready-for-agent

- [ ] Before requesting the registration challenge, the browser generates every piece of local bootstrap material: client-minted UUIDv7 Account ID, hidden root Directory node ID, and device ID; a non-extractable P-256 HPKE transport key pair and a separate non-extractable P-256 device-assertion signing key pair; the Vault root key, root Directory capability key, and that capability's `vault-recovery` Key envelope; the first device's `device-enrollment` Key envelope carrying the Vault root key; the 256-bit Vault recovery secret and its 24-word phrase, the public recovery salt, the recovery-enrollment key pair, the generation-1 Recovery capsule, and the matching recovery-verification public key; the encrypted Account profile carrying the generated Public pseudonym; and ten authentication recovery-code hashes.
- [ ] Global and network registration-challenge limits are applied before a challenge is created; the challenge is random, registration-purpose-bound, and five minutes long.
- [ ] Browser proof of work finds an 8-byte nonce such that `SHA-256(challenge-bytes || nonce)` has 18 leading zero bits; a proof submission, valid or invalid, consumes the challenge atomically.
- [ ] A non-empty hidden registration honeypot is rejected generically and its value is neither persisted nor logged.
- [ ] WebAuthn registration completes with attestation disabled; the registration challenge is a domain-separated digest of the canonical signup transcript (Account ID, device ID, both candidate public keys/transcript digest, capsule generation/metadata digest, recovery-verification public key, registration challenge material, proof-of-work material, and initial registry epoch), so `clientDataJSON.challenge` cannot match if any bound value changes.
- [ ] The browser signs a canonical `mdwn/signup-device-binding/v1` statement with the candidate device-assertion private key, and the service verifies it before activation.
- [ ] One short D1 transaction creates all-or-nothing: the Account, the first passkey, the encryption identity/device registry at epoch 1, the first Encryption device in `active` state with opaque approval provenance `signup`, both initial Key envelopes, the generation-1 capsule, the ten-code authentication recovery set, and a normal Session already bound to that exact device. No Account may exist whose capsule or root-capability envelope is missing or deferred, and signup creates no `crypto_jobs` row or provisioning need.
- [ ] A substituted candidate key, altered transcript or capsule digest, replayed or mismatched registration challenge, replayed proof of work, missing candidate private key, and invalid binding statement all fail without creating an Account; a failed or interrupted signup leaves no partial Account.
- [ ] The 24-word phrase is shown with a mandatory verification step (re-entering three words) and the ten recovery codes once; only code hashes and opaque capsule material are persisted. Until confirmation, a client-local gate blocks File creation, Directory creation, and Import, with no server flag recording it.
- [ ] The signup Session is never unprovisioned and there is no grace period or bootstrap credential: the first private operation requires the ordinary `mdwn/device-proof/v1` at the current registry epoch exactly as any later operation does.
- [ ] If the commit succeeded but its response was lost, signing in with the passkey plus bind-on-sign-in (ticket 09) rebinds the Session with no QR, no registry-epoch change, and no duplicate Account; if the commit never happened, signup restarts under fresh rate limits and an orphaned authenticator credential is the only residue.
- [ ] The only bootstrap UI states are **Creating your account…**, the phrase display and verification gate, and generic retry guidance on failure; **Setting up your Files securely…** and **Shared content is being securely provisioned** never appear during signup.
