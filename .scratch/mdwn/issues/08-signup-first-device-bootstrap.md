# 08: Signup: first-Encryption-device bootstrap, phrase gate, recovery codes

**What to build:** A new person creates an mdwn Account in one ceremony — proof of work, then a passkey — and lands signed in on a browser that is already a private-capable, device-bound Encryption device, with the Vault recovery phrase recorded and ten authentication recovery codes shown exactly once.

**Blocked by:** 03 (`mdwn/enc-v1` envelope library), 04 (Vault key hierarchy, recovery secret, and capsule), 06 (Accounts, passkeys, sessions), 07 (Abuse-control primitives).

**Status:** done

**Scope boundary:** This ticket owns the device-proof primitives, device-key persistence, and bind-on-sign-in needed to accept signup independently. Ticket 09 builds on these interfaces for comprehensive private-route enforcement, registry-epoch changes, and device-loss coverage; signup has no implementation dependency on ticket 09.

- [x] Before requesting the registration challenge, the browser generates every piece of local bootstrap material: client-minted UUIDv7 Account ID, hidden root Directory node ID, and device ID; a non-extractable P-256 HPKE transport key pair and a separate non-extractable P-256 device-assertion signing key pair; the Vault root key, root Directory capability key, and that capability's `vault-recovery` Key envelope; the first device's `device-enrollment` Key envelope carrying the Vault root key; the 256-bit Vault recovery secret and its 24-word phrase, the public recovery salt, the recovery-enrollment key pair, the generation-1 Recovery capsule, and the matching recovery-verification public key; the encrypted Account profile carrying the generated Public pseudonym; and ten authentication recovery-code hashes.
- [x] A reusable browser device store generates both private keys with `extractable: false` and persists their WebCrypto `CryptoKey` handles by structured clone into IndexedDB, alongside the opaque device ID and cached registry epoch. Keys are never self-wrapped; the app requests `navigator.storage.persist()`. Tests prove possession after tab close, sign-out, and full browser restart in Chromium, Firefox, and WebKit. A missing or unreadable key cannot silently produce a replacement device or a private-capable Session.
- [x] Global and network registration-challenge limits are applied before a challenge is created; the challenge is random, registration-purpose-bound, and five minutes long.
- [x] Browser proof of work finds an 8-byte nonce such that `SHA-256(challenge-bytes || nonce)` has 18 leading zero bits; a proof submission, valid or invalid, consumes the challenge atomically.
- [x] A non-empty hidden registration honeypot is rejected generically and its value is neither persisted nor logged.
- [x] WebAuthn registration completes with attestation disabled; the registration challenge is a domain-separated digest of the canonical signup transcript (Account ID, device ID, both candidate public keys/transcript digest, capsule generation/metadata digest, recovery-verification public key, registration challenge material, proof-of-work material, and initial registry epoch), so `clientDataJSON.challenge` cannot match if any bound value changes.
- [x] The browser signs a canonical `mdwn/signup-device-binding/v1` statement with the candidate device-assertion private key, and the service verifies it before activation.
- [x] One short D1 transaction creates all-or-nothing: the Account, the first passkey, the encryption identity/device registry at epoch 1, the first Encryption device in `active` state with opaque approval provenance `signup`, both initial Key envelopes, the generation-1 capsule, the ten-code authentication recovery set, and a normal Session already bound to that exact device. No Account may exist whose capsule or root-capability envelope is missing or deferred, and signup creates no `crypto_jobs` row or provisioning need.
- [x] A substituted candidate key, altered transcript or capsule digest, replayed or mismatched registration challenge, replayed proof of work, missing candidate private key, and invalid binding statement all fail without creating an Account; a failed or interrupted signup leaves no partial Account.
- [x] The 24-word phrase is shown with a mandatory verification step (re-entering three words) and the ten recovery codes once; only code hashes and opaque capsule material are persisted. Until confirmation, a client-local gate blocks File creation, Directory creation, and Import, with no server flag recording it.
- [x] The signup Session is never unprovisioned and there is no grace period or bootstrap credential: the first private operation requires the ordinary `mdwn/device-proof/v1` at the current registry epoch exactly as any later operation does.
- [x] Reusable `mdwn/device-proof/v1` generation and verification bind a Session-binding digest, device ID, current device-registry epoch, HTTP method, canonical path/query, body digest, issued/expiry time of at most five minutes, and a random proof ID. The service checks the signature, matching bound normal Session, active device state, and current epoch before the first private operation. Tests reject missing, mismatched, expired, stale, and invalid proofs at this boundary.
- [x] The proof primitives atomically consume mutation and security-sensitive proofs with the action's expected revision/idempotency condition. A read-only proof is request-bound and expires but is not persistently consumed; replay cannot change state and no workspace read creates a D1 write. Tests cover both behaviors at the shared authorization boundary.
- [x] Bind-on-sign-in is implemented here: a normal Session created by a fresh Passkey assertion may become bound to an already-active device when the browser proves possession of its persisted keys at the current registry epoch. It applies only at Session creation; it never activates a device, changes the epoch, or replaces/approves anything. A failed proof, missing key, or revoked or tombstoned device leaves the Session unprovisioned and unable to access private material.
- [x] If the commit succeeded but its response was lost, signing in with the passkey plus bind-on-sign-in rebinds the Session with no QR, no registry-epoch change, and no duplicate Account; if the commit never happened, signup restarts under fresh rate limits and an orphaned authenticator credential is the only residue. Cross-engine tests prove the lost-response sign-in path with the persisted device keys.
- [x] The only bootstrap UI states are **Creating your account…**, the phrase display and verification gate, and generic retry guidance on failure; **Setting up your Files securely…** and **Shared content is being securely provisioned** never appear during signup.
