# Data model & schema

## Question

Design the relational schema that everything else writes through:

- `users` (identity, credentials).
- `folders` — the tree. Adjacency list (`parent_id`) vs materialised path; decide based on how moves and permission checks will be written.
- `files` — `content` column, title, slug, timestamps; where does markdown source live if the privacy model chooses encryption?
- `shares` and `public_links` — two separate tables, matching the two mechanisms (`05`, `06`).
- `comments` (`07`).
- Uniqueness/constraints: can two files in one folder share a name? Two folders?
- Deletion semantics: soft vs hard delete, cascade on folder delete.
- Own the canonical domain glossary: write it into `CONTEXT.md` here.

## Answer

**Resolution — encrypted D1 adjacency-list graph.** mdwn uses SQLite-compatible D1 tables with opaque IDs and explicit lifecycle records. There is no `users`, plaintext `content`, `title`, `slug`, filename, or plaintext directory-order column.

### Conventions

- Application-visible Account, File, and Directory IDs are canonical UUIDv7 `TEXT` values. Public-link path IDs are independently generated 256-bit random base64url values and are never reused.
- Server timestamps and monotonic revisions are `INTEGER`; ciphertext and `mdwn/enc-v1` envelopes are `BLOB`. Every private payload is encrypted in the browser before transmission.
- IDs, node type, parent relation, ciphertext size, server timestamps, access records, key epochs, and public encryption keys are permitted metadata. Names, ordering, Markdown, front matter, user-authored timestamps, Comment text, and displayed pseudonyms are not.

### Accounts, authentication, and client encryption

- `accounts` contains the opaque Account ID, opaque unique share identifier, optional unique normalized **lookup token** for a share handle, and server lifecycle timestamps. It stores no email, password, plaintext handle, or plaintext pseudonym. There is no account discovery: a Share lookup is exact-match only.
- An encrypted `account_profiles` representation holds private Account-facing data, including the current Public pseudonym. Its values are separately re-encrypted for each Comment-thread or Publication-attribution context where that pseudonym is displayed.
- `passkeys`, `webauthn_challenges`, `recovery_codes`, `sessions`, and `security_events` are separate tables. Passkeys store only credential public material and counter/backup metadata; challenges are deleted after use; recovery-code values are stored only as hashes and consumed codes are removed; sessions have purpose (`normal` or restricted `recovery`), credential association, expiry, and revocation state.
- `encryption_identities` and `encryption_devices` store Account encryption public keys, device approval, and revocation state. Vault-recovery material is only a Key envelope ciphertext; the Vault recovery secret itself is never stored by the service.

### Private hierarchy and File representations

- `vault_nodes` is the single typed graph: `id`, `kind` (`directory` or `file`), `owner_account_id`, nullable `parent_node_id`, nullable immutable `import_id`, and server lifecycle metadata. Each Account has exactly one hidden root Directory, enforced by a partial unique root constraint. A Share never copies another Account’s nodes into a recipient tree. `import_id` is absent for a normal create; every canonical record created for a staged import carries the same `import_id`, whose committed marker is required for normal visibility.
- `directories` extends a Directory node with its opaque `entries_revision`. `files` extends a File node with `current_representation_id` and `current_revision`.
- `directory_entries` is one encrypted record per current parent/child edge. It contains the encrypted display name and ordering value plus the parent-directory Key envelope for the child Directory capability or current File content key. Its parent/child edge agrees with `vault_nodes.parent_node_id` in the same transaction. A File save refreshes its File-key envelope without changing the structural entry revision. For an import performed through a Directory Grant, the browser uses the current target Directory capability to wrap each new child Directory capability or File content key; it creates no new Share, Grant, or special Owner envelope.
- `file_representations` stores a File’s encrypted current Markdown and File metadata, content-key/epoch identity, ciphertext size, and revision. The encrypted metadata supplies the standalone label for a direct File Grant, never a parent path. A save inserts a fresh representation, conditionally swaps the File pointer only when the browser’s expected revision matches, replaces the parent-entry and every active direct-Grant envelope for the fresh content key, and then removes the superseded representation. This is not version history.
- A Directory has one normalized, case-insensitive namespace across Files and Directories. The browser decrypts entries, rejects duplicate normalized names, and conditionally increments `entries_revision` with every create, rename, reorder, delete, or move. Concurrent structural changes conflict and refresh/retry; the service receives no plaintext or deterministic name-equality token.

### Key envelopes and sharing

- `key_envelopes` is the one constrained wrapping graph: protected-object/key identity, purpose, recipient identity, epoch, versioned envelope ciphertext, and current/superseded lifecycle metadata. Its purposes cover Directory edges, active Grants, device enrollment, Vault recovery, Publications, Private Comment threads, Public Comment audience epochs, and encrypted attribution. A public-epoch envelope targets the active Publication link; an authenticated-history envelope targets an enrolled eligible device. Cross-table target-type, recipient, current-access, and authenticated-context rules are validated transactionally.
- Pending account-to-account invitations live in `shares`: Owner, recipient Account, target node, proposed permission, and pending lifecycle data. A pending Share is unique per Owner, recipient, and target.
- Accepted authorization lives in `grants`, not `shares`. An active Grant is unique per Owner, recipient, and target and carries the read/write permission. Its recipient-device Key envelopes provision the currently authorized encryption identities. Cancelled/declined Shares and revoked Grants are hard-deleted after any bounded security retention; MVP has no historical sharing audit log.
- Effective File access is the union of active Grants on an exact File or an ancestor Directory, evaluated with a bounded recursive CTE; its strongest permission controls Markdown and structural operations. The same query derives both `can_read_private_comments` and `can_read_collaborators_public_comments`: an Owner or any Account with one or more active File-read Grants has each, regardless of Grant permission. An active Publication and its selected audience remain separate endpoint checks. Only the Owner may create/change Grants. Containment ownership stays with the Directory Owner: an import initiator must own the target Directory or hold a current read/write Directory Grant at both staging and commit, and every new import descendant receives that target Owner’s `owner_account_id`; direct File and read-only Grants never qualify. Cross-owner moves are rejected.
- `import_sessions` binds an unguessable session to the initiating Account, target Directory, expected target Owner, reviewed target revision, encrypted manifest digest/counts, and expiry; `import_chunks` holds its encrypted uploads. An `import_commits` row is the immutable visibility marker. The final transaction rechecks the initiating Account, target Owner, current import authority, structural/key constraints, reviewed revisions, and collision actions before writing that marker. Imported descendants then follow ordinary containment-based Grants and Key rotation; a revoked Grant or stale target leaves no commit marker and no visible tree.
- Revoking a Directory Grant removes server authorization in a short transaction, advances the affected epoch, blocks new writes below the root, and creates an opaque `crypto_jobs` Key-rotation record. Remaining authorized browsers perform bounded rewrapping batches; no plaintext keys or content enter the job. A move out of a shared subtree must complete its required rekey in the bounded operation or is rejected/deferred rather than exposing future writes under an old capability.

### Publications and Comments

- `publications` is the logical per-File publication record: File, Owner, `active` or irreversible `deleting` state, current link and public-representation pointers while active, comment audience, and lifecycle timestamps. `deleting` is a sealed teardown marker, not an unpublished/archive state and cannot become active again. A partial unique constraint permits at most one active-or-deleting Publication per File, so a fresh Publication waits for teardown completion. `publication_teardowns` holds only the opaque Publication/Owner reference and bounded deletion cursor/progress; it is inaccessible through every reader route and is deleted with the terminal Publication record.
- `publication_links` holds only the active opaque path ID and publication encryption public key. Its paired decryption capability remains in the URL fragment. Rotation atomically installs a fresh link/key and removes the old link so it returns the same ciphertext-free `404` as an unknown link.
- `public_representations` is separate from `file_representations`. A File save with an active Publication conditionally updates both encrypted representations in the same transaction. Authorized File editors encrypt the public representation with the stored public encryption key but never receive the URL-fragment capability or Publication-management authority. It becomes unreachable in the short unpublish seal transaction and is explicitly hard-deleted by the bounded Publication teardown.
- `publication_requests` records one pending Collaborator request per File; approval creates a Publication, while denial/cancellation removes the request. `publication_authors` stores selected encrypted author-attribution declarations.
- `comment_threads` has exactly one Private thread per File and one Public thread per logical Publication. A Public thread has ordered `comment_thread_epochs` with immutable audience (`public` or `collaborators_only`), key epoch, and lifecycle metadata; every `comments` row references its thread and audience epoch, plus its opaque author Account reference, server ordering sequence/timestamps, and encrypted plain-text body/pseudonym data. `thread_attributions` and `publication_authors` hold the encrypted current pseudonym declaration for their scope; an author/attributed Account receives a matching Key envelope so its browser can update it.
- A Private-thread capability has a current Key envelope for every authorized Account/device with `can_read_private_comments`; overlapping Grant paths do not duplicate or strengthen that capability. Private-thread reads and creates require that current authorization and epoch. Updating or hard-deleting a Comment additionally requires matching `author_account_id`; a File Owner may hard-delete any Comment but cannot update another author’s ciphertext. When an Account loses its last File-read Grant, the server denies future Private-thread access and mutation, and the established revocation/epoch-rotation process rewraps the capability only for remaining authorized Accounts. A Private thread created by import is freshly provisioned for current File-read access; historical imported Comment data does not reinstate former thread capabilities or authors’ mutation authority.
- A Public epoch is readable on the anonymous route only when its Publication is active with a public audience; it has a Publication-link envelope plus device envelopes for the Owner and every Account with effective File-read access. A Collaborators-only epoch has only those direct device envelopes. Grant/device acceptance provisions retained epochs in bounded browser-driven batches; loss of the last File-read path denies access, supersedes device envelopes, and rotates the current Collaborators-only epoch for remaining devices. Audience changes create fresh epochs, so the anonymous route never receives a Collaborators-only epoch. Link rotation replaces only public-epoch link envelopes. Unpublish first removes the link and denies every Public-thread route, then its teardown explicitly deletes every Public thread, epoch, Comment, envelope, attribution, representation, request, and Publication record. A later Publication is fresh.
- A Public-pseudonym change creates an exclusive, browser-driven `crypto_jobs` batch. The UI shows progress and blocks normal work; all contexts retain the old pseudonym until every encrypted attribution update succeeds and the new Account profile becomes current atomically. An enrolled device can resume an interrupted batch.

### Integrity, transactions, and deletion

- D1 foreign keys, `CHECK` constraints, opaque-ID uniqueness, and partial unique indexes enforce row-local facts. Foreign keys use `ON DELETE RESTRICT`; generic cascades never perform a privacy-sensitive product action.
- Short application transactions enforce directory-only parents, same-owner containment, no cycles, Grant scope/authorization, eligible Import targets, import target-Owner assignment, committed-marker visibility, Private Comment current-access and author-or-Owner mutation rules, current key epochs, structural revisions, and File save revisions. Representative tree queries must use indexes beginning with `parent_node_id` and be checked with `EXPLAIN QUERY PLAN`; recursive traversal is bounded.
- File deletion explicitly removes its Directory entry, representations, Key envelopes, Shares/Grants, Publication requests/records/links/representations/teardowns, and both Comment threads before the node. Directory deletion enumerates the subtree, confirms authorization and a maximum of 500 nodes, and explicitly removes all dependent graph records in one transaction. A Collaborator cannot delete a shared root.
- Owner-confirmed unpublish uses a short transaction to verify ownership, count opaque Public Comments for its irreversible confirmation, remove the active link, and create the non-restorable teardown marker. It then accepts only owner-authenticated, idempotent bounded cleanup batches; interruption remains sealed, and only completion removes the marker and permits a new Publication. Public-participation limits never block this security/deletion action.
- There is no trash, soft-delete state, restore action, or user-visible revision history. An oversized Directory delete makes no change and is deferred beyond the MVP to a separately designed resumable hard-deletion workflow. Provider-managed backups and already downloaded plaintext remain outside the application-level hard-deletion guarantee.
