# RR8 post-review gate

Run this **after** the ordinary code review, against the **same pinned diff**. This is a focused framework/stack check, not a replacement for the review's Standards and Spec axes. Review only; make changes only when the user asks for a fix.

1. **Pin scope.** Reuse the review's fixed point and diff command (including working-tree changes if that review included them); do not silently substitute `main` or review a different commit. List changed routes, UI data consumers, resource endpoints, Worker/database boundaries, and relevant tests. Trace each changed data flow from component to route to Worker. If no such paths changed, report **Not applicable — no RR8/stack touchpoints**, not an unqualified pass. Ask for the fixed point if the reviewed diff is unknown.
2. **Resolve the actual contract.** Read `package.json`/lockfile, `react-router.config.ts`, `app/routes.ts`, `docs/buildable-spec.md` §3, `docs/serving-and-security.md` §1, `docs/testing.md`, and ADR-0002 where relevant. Use the **installed** React Router version/types and current [client data](https://reactrouter.com/how-to/client-data), [fetchers](https://reactrouter.com/how-to/fetchers), and [race conditions](https://reactrouter.com/explanation/race-conditions) docs for API claims. If the change touches Workers behavior, check the configured runtime and current Cloudflare docs as well. Repository privacy rules override generic SSR advice; note any uncertain version-specific claim instead of guessing.
3. **Check every touched boundary:**
   - **Loading/SSR:** Is route data obtained through `loader` or `clientLoader` rather than an effect-driven request where route data would fit? Does initial SSR render only the shell/non-sensitive data? For browser-only Account or private data, use a `clientLoader` with a public `HydrateFallback`; audit HTML/hydration payloads and `.server` import boundaries. `clientLoader.hydrate = true` is implicit **only when no server `loader` exists**; check mixed loaders explicitly.
   - **Mutations:** Are ordinary server interactions in route `action`/resource actions and submitted with `<Form>`, `fetcher.Form`, or `useFetcher`/`clientAction` when appropriate? Are pending, error, redirect, cookie, and automatic revalidation states handled, including controls staying busy through revalidation? Follow abort signals for browser fetches and look for stale-response UI races. Router cancellation does **not** make Worker/database writes atomic.
   - **Browser-only work:** WebAuthn, WebCrypto, and IndexedDB legitimately run in browser code. A `clientAction` may orchestrate their resource-route HTTP calls; the Worker must still verify authorization and mutations. A direct `fetch()` or a `useEffect` is **not** itself a finding when needed for browser APIs, subscriptions, or a documented exception. Identify the actual lifecycle or security consequence before flagging it.
   - **Chosen stack:** Worker bindings and `app/shared/db/client.server.ts`/Drizzle are the D1 boundary; `createSessionStorage` uses D1 for Session authority. Check same-origin mutations, secret/client-bundle separation, and relevant migration/runtime constraints when touched. Check coverage via `SELF.fetch` for route boundaries and cross-engine browser tests for browser ceremonies/SSR. Apply existing repo docs, not a blanket rule from another RR deployment target.
4. **Report evidence.** For each actionable issue give severity, changed `file:line`, the violated repo rule or official API source, a reproducible consequence, and a concrete RR8-native alternative. Distinguish documented-rule violations from best-practice judgement calls; distinguish UI staleness from an authorization bypass. Say which checks/tests ran versus which were only inspected. Finish with **Pass**, **Findings**, **Not applicable**, or **Unverified** (with the missing evidence). Account for every changed RR8/stack data-flow site before declaring Pass.

When invoked alongside the two-axis `code-review` skill, complete that skill's Standards and Spec reports as required, then present this gate as a **separate follow-up result**, without merging or reranking its findings into either axis.
